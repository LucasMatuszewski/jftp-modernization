# Behavioral regression test design

This is a proposal for four whole-application regression suites. No test code was added or run during the documentation phase. The current POM declares JUnit 3.8.1 but the repository has no tracked test classes; the two tracked test files are empty placeholders ([build and dependencies](build-and-dependencies.md)). Design and write the suites first. If legacy compiler or dependency issues prevent them from compiling, make only the narrow bootstrap changes needed to execute the baseline before launcher/startup fixes or broader changes. Do not interpret bootstrap failures as application regressions.

## Test layers and evidence

Use pure unit tests for deterministic value transformations and isolated state rules: extension-to-transfer-type selection, remote-host settings, favorite duplicate identity, filter decisions, resource-bundle lookup and help-map references. Unit tests should not stand in for the transfer contract.

Use integration tests that invoke JFTP application/session actions against a controlled loopback FTP server for session, file, transfer and FTPS contracts. Keep all input/output under a per-test temporary user home and temporary local tree. Configure a deterministic server fixture with fixed response sequences, passive data ports, an isolated remote filesystem, and explicit binary and ASCII behavior. Avoid public servers, user home state, network dependencies and shared ports. The fixture must expose server-side files and control/data command outcomes so assertions cover observable output and state.

Use UI smoke tests for startup, tab/session navigation, preferences/favorites dialogs, help, status display, Desktop handoff where the OS supports it, certificate prompts, and menu/toolbar enablement. Run headless only for tests that do not require native desktop services. Do not claim Java applet/browser smoke support on a current JDK; treat the applet target as a compatibility question.

After every runtime change, also exercise the real Swing application through the affected flow using available computer-use tooling or a Computer Commander MCP, under isolated synthetic state. Capture changed screens, verify completion/cancellation and relevant failures, and inspect application/server logs; transfer changes require destination-byte/path checks, and packaging changes require launching an extracted distribution outside the IDE. Record steps, outcomes, environment, and screenshot/log locations. If desktop access is unavailable, report the blocked Manual QA and obtain human verification before declaring runtime work complete. Automated tests alone do not prove the running application works. Documentation-only changes require content/link/consistency checks, not an application launch.

When the app APIs require a displayed Swing session, classify the suite as integration/UI and show the session under a test display. Do not replace that boundary with direct calls to FTPAPI alone. Assert transferred bytes or server filesystem state, selected-session output, status/transcript messages, prompt outcomes, or persisted compatibility state. Avoid assertions on private fields, helper class choice, or thread implementation.

## Four example behavioral suites

### 1. Startup, session selection, preferences and favorites

Launch the desktop application with an isolated temporary `user.home`. Verify that first startup creates usable default preferences; a session begins disconnected, can open multiple tabs, and toolbar/menu commands apply to the selected tab. Save and reload representative locale/theme, local directory, passive mode, extension transfer mapping, proxy disabled, certificate-store path, and update-check setting. Add, edit, sort, reject duplicate, connect from, and delete favorites; verify fields such as label, host, port, user, account, client/parser choice, initial directories, commands and SSL mode survive the favorites round trip. Exercise connection validation at port endpoints 0 and 65535, required fields containing only whitespace, and implicit SSL port validation only when that mode is selected. Confirm whitespace is used for validation but approved host/user/password/path/command strings retain their entered value. Never assert real credentials or use an actual proxy/server.

The current persistence formats are Java serialization for `preferences.ser` and a `SealedObject` wrapper for `favorites.ser`; tests should use synthetic values and a fresh temporary home. Include compatibility fixtures only if a safe synthetic legacy plaintext favorite list can be generated. Treat the fixed-key wrapper, object deserialization, and plaintext preference password fields as current storage facts, not a desired security contract. The suite should verify the migration policy selected for implementation rather than freeze unsafe storage indefinitely.

### 2. Local and remote browser behavior

Use a dedicated temporary local tree and isolated remote fixture tree. Exercise changing/up-directory navigation, refresh, select-all/invert, independently applied and cleared filters, create file/directory, rename, confirmed delete, properties, and local/remote open behavior for files and directories. Check that cancelled dialogs leave the filesystem unchanged and that successful operations refresh the visible listing. After sorting, verify the selected file still corresponds to the intended row; exercise selected-row and blank-area context popups because one preserves multi-selection and the other clears it. Verify ascending/descending directory placement and the remote attributes column's unsortable behavior. Cover inclusion/exclusion, empty criteria, regex errors, lenient date input, the local hidden-file/exclusion interaction, and directory pass behavior. For remote tests, assert FTP server filesystem results and returned listing names; for local tests, assert only within the temporary fixture root.

Use names with spaces, non-ASCII Unicode, mixed case and leading/trailing dots where the existing UI accepts them. Record platform-sensitive Desktop open/edit/print capability rather than requiring an editor or printer in integration runs. Verify remote recursive properties restore the prior working directory after traversing filtered children, preserve the file type character while updating permission bits, and skip `.`/`..`. Current-source discrepancies such as asynchronous versus synchronous refresh, platform Desktop support, permission-command ordering, and null/error handling should be written as observed findings; do not codify an accidental failure as required behavior without product evidence.

### 3. Transfer and archive workflows

Exercise the actual JFTP `FTPSession` upload/download actions (or visible actions when necessary) against a deterministic FTP fixture. At minimum, upload a local binary fixture, assert exact remote bytes, download it, and assert exact local bytes. Add ASCII newline conversion as an explicit expected behavior case, plus a Unicode filename and nested directory to cover normalization and recursion. Include “upload as” and “download as” destination names, multiple selections, extension auto-detection, manual ASCII/binary override, and progress/status completion.

Configure server responses for a permission/transfer rejection and a data-channel failure; assert a user-visible error/transcript and that no success state is reported. For cancellation, use a gated data transfer that pauses after a known byte boundary, invoke the application abort action, then assert termination, the aborted status callback, final output state, and that later selected files are not transferred. Make retries and timeouts deterministic. Exercise ZIP download/extract and local zip/upload only with controlled fixtures and temporary roots. Cover temporary/current/chosen archive destinations and the post-operation delete option, including filenames with spaces and Unicode. ZIP path traversal rejection is a future security-fix case that should fail against unsafe legacy behavior until fixed; do not mark unsafe extraction as a passing compatibility expectation.

Assertions must be on destination bytes, server-side paths, visible/session state, completion/error/cancel callbacks or status, not internal transfer loops, FTPAPI fields, helper classes, or thread counts. Test binary data that includes zero bytes and high bytes; keep expected ASCII conversion explicit and separate from binary equality.

### 4. FTPS certificate and trust decision workflows

Use a loopback FTPS fixture with a generated certificate and controlled variants: valid matching hostname, untrusted chain, hostname mismatch, expired/not-yet-valid leaf, and TLS handshake failure. Exercise explicit and implicit FTPS paths, both encrypted and configured unencrypted data channels where the server fixture supports them. Verify which warning appears, the default/reject outcome, accepted session behavior, secure indicator, disconnect/reconnect result, and whether a separately installed certificate remains in the configured synthetic server store after restart. Do not use public trust stores or the developer's real JKS files.

Separate characterization from target security behavior. The current custom trust manager can accept a chain after a user confirmation even when dates or host name fail, and acceptance is cached in memory; permanent trust installation is a separate action ([TLS and persistence](tls-and-persistence.md)). Characterize the visible decision boundary so modernization preserves a clear prompt and connection result, but write fail-first regression cases for corrected hostname, validity and PKIX verification as explicit security fixes. Once corrected, those cases must reject unsafe chains regardless of prior in-memory acceptance unless the approved policy explicitly says otherwise. Never loosen assertions to accommodate a security regression.

## Bootstrap, red/green and phase gates

Write these four suites before implementation changes. If the legacy code or test source cannot compile, make only the narrow compiler/tool/dependency bootstrap changes needed to make a baseline executable; then capture build and test output before launcher/startup fixes or broader changes. Resolve and document the FTPAPI artifact's availability, API surface and redistribution rights before replacing it. The old compiler plugin/source target, custom HTTP repository, unverified external FTP API, JavaHelp dependency, and package/launcher path mismatch can prevent a first compile or app launch; record each bootstrap failure separately from test failures. Do not claim the baseline is green until a build and each test layer actually runs.

For every implementation change, preserve the failing test output as red evidence, make the smallest behavior change, then capture the same test passing as green evidence. Keep characterization tests for existing behavior distinct from intended bug-fix tests. A known unsafe or incorrect behavior may be documented as a current defect and an expected fail-first security/correctness test; do not require preserving it. Do not change an assertion or remove a test only because a refactor regressed observable behavior.

Candidate test stack: JUnit 6.1.3/Jupiter with a Java 21 bootstrap, and Maven Surefire 3.6.0 or compatible (current documentation researched 2026-10-06). The POM currently declares JUnit 3.8.1, which can remain only for a narrow initial bootstrap if required. Verify exact plugin compatibility and controlled-server fixture support during implementation. Keep dependencies, server process, certificate fixture generation, GUI display and test ports deterministic and isolated. Each phase should update this design, the applicable source/agent instructions, and the integrated modernization plan if it changes behavior, commands, dependencies or test boundaries.

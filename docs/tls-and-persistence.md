# TLS, certificates, and persisted state: current behavior

This page combines direct source inspection of the owned TLS package with caller and persistence facts supplied by the application-workflow delegate. It describes checked-in behavior; it does not claim a successful build, runtime TLS handshake, or test. Links are relative to this document.

## Protocol and certificate inventory (2026-10-06)

Built-in connection modes are plain FTP (no TLS) and FTPS (SSL if available, explicit, implicit); the UI also permits an unencrypted FTPS data channel. FTPS applies TLS to FTP control/data connections and uses X.509 certificates in the app's JKS trust path. No built-in SSH/SFTP implementation is evidenced. The configured `FTPClient` class is extensible, so a supplied custom implementation could add protocols. Source asks for algorithm alias `SSL`/`SunX509`; that alias does not prove SSLv3 configuration, and without a build and handshake the negotiated TLS version is unknown. Repository metadata contains zero tracked certificate/key/store candidates with common certificate suffixes. The coordinator's existence-only check found the two default profile JKS files absent; no profile contents were read, and Windows/system stores or arbitrary configured paths were not inventoried. See [protocol and certificate modernization options](security-modernization-options.md) for scoped inventory details, official RFCs, and candidate directions.

## Connection and trust flow

`FTPSession.connect` creates the FTP client/parser from the selected `RemoteHost`, applies passive mode, timeout, buffer size, SSL mode, and data-channel encryption settings, then calls [`JFTPSSLContext.getSSLContext`](../src/main/java/com/myjavaworld/jftp/ssl/JFTPSSLContext.java#L38) for SSL-enabled modes before registering control/data/FTP listeners and connecting. The caller uses the remote host name as the TLS host-name argument; SSL mode also controls implicit-port selection. This means TLS context construction and trust decisions occur before the FTP connection proceeds.

`JFTPSSLContext.getSSLContext` requests provider algorithm name `SSL`, creates a new [`JFTPKeyManager`](../src/main/java/com/myjavaworld/jftp/ssl/JFTPKeyManager.java#L39) and [`JFTPTrustManager`](../src/main/java/com/myjavaworld/jftp/ssl/JFTPTrustManager.java#L52), and initializes the context with those one-element manager arrays. The connection does not rely on the platform's ordinary default trust manager: the wrapper initializes `TrustManagerFactory` with the application's server-certificate JKS. Both key and trust manager factories request provider algorithm `SunX509`, which is a provider-name compatibility assumption.

### Current server-certificate decision

`JFTPTrustManager.checkServerTrusted` compares the incoming chain with the last chain stored on that trust-manager instance. If `Arrays.equals` matches, it returns immediately. Otherwise it computes three flags and calls `SecurityWarningDlg.showDialog` whenever any flag is false:

- `isValidDate` checks only `chain[0]` (the leaf) with `checkValidity()`; it does not validate every chain certificate here.
- `isValidHost` reads only the leaf's subject common name through `getSubjectDN()` and `DNParser`; it compares case-insensitively with the requested host. It does not inspect subject alternative names, wildcard names, or IP address SANs.
- `isTrusted` looks for any certificate from the supplied chain in the configured server keystore using exact certificate equality. It does not call the initialized delegate's `tm.checkServerTrusted` from `checkServerTrusted`; signature/path building and other PKIX checks from that delegate are therefore not performed on this custom path.

If any check fails and the user chooses No, `checkServerTrusted` throws `CertificateException("No trusted certificate found.")`. If the user chooses Yes, the entire chain is cached in this trust-manager instance and accepted for subsequent byte-equal chains without repeating the checks. The current dialog therefore allows a user to proceed despite invalid dates, name mismatch, or an untrusted chain. Acceptance does not itself write trust to disk. `getAcceptedIssuers()` does delegate to the configured trust manager; `checkClientTrusted()` delegates as well.

These behaviors expose important current security defects and policy questions. The leaf-only CN comparison does not implement modern hostname verification; the custom method omits standard PKIX validation; user acceptance of any failed condition applies to the current manager/session. These defects are documented so they are not mistaken for desirable security contracts. Correcting certificate validation and reducing what Yes can override are security fixes, but any visible prompt/acceptance change must be made as an explicit product policy decision and covered with controlled FTPS cases.

### Certificate UI and import behavior

[`SecurityWarningDlg`](../src/main/java/com/myjavaworld/jftp/ssl/SecurityWarningDlg.java#L54) reports the three booleans, defaults to No, treats Escape as No, and opens a certificate viewer that can install the presented chain. `CertificateDlg` calls `KeyStoreManager.addServerCertificate(chain)` only when Install is selected; errors are shown through `GUIUtil.showError`. Thus permanent trust is an explicit separate action from the warning's Yes/No response.

[`CertificateManagerDlg`](../src/main/java/com/myjavaworld/jftp/ssl/CertificateManagerDlg.java#L58) displays the server-certificate tab; the client-certificate tab construction is commented out. It supports viewing/importing server certificates, and a Delete-key action invokes certificate deletion after confirmation. Client import/delete helper methods remain in source but are not reachable from a visible tab. Import uses `CertificateFactory.getInstance("X.509").generateCertificates`, then adds each returned certificate as a separate certificate entry. It does not import private keys or PKCS#12 identity containers. The table lists certificate entries only, with organization extracted from issuer/subject DNs and validity dates; `CertificatePane` displays properties from `chain[0]` and parses issuer/subject DNs with a simple string parser. `DNParser` splits on the first matching `PARAM=` and then on comma or quote; it is not a full RFC 2253 distinguished-name parser.

[`CertificateTableModel`](../src/main/java/com/myjavaworld/jftp/ssl/CertificateTableModel.java#L42) enumerates aliases for which `KeyStore.isCertificateEntry(alias)` is true. It returns the subject/issuer organization, not the complete distinguished name, and catches `KeyStoreException` during rendering as a literal error string. Certificate view and import errors are displayed; some delete/reload errors are only printed to stderr.

## Keystore files and identity material

[`KeyStoreManager`](../src/main/java/com/myjavaworld/jftp/ssl/KeyStoreManager.java#L35) lazily initializes two process-wide stores from `JFTP.prefs`: server certificates and client certificates. Both use the explicit `JKS` keystore type and raw path strings supplied by preferences. If a configured file does not exist, it creates an empty JKS then writes it before loading it. The containing directory must already exist. Store writes go directly to the destination through `FileOutputStream`; they are not atomic or staged. Errors are wrapped as `KeyStoreException`; load retains the underlying exception text, while save reports a generic failure with the file path.

By default the files are `${user.home}/.jftp/data/serverCertificates.jks` and `${user.home}/.jftp/data/clientCertificates.jks`; the preference values are raw path strings. Both keystore passwords default to the literal `changeit`. Aliases for newly stored certificates are `JFTP1001`, then one above the largest parseable existing JFTP numeric suffix. Adding a certificate already present by `KeyStore.getCertificateAlias` replaces its current entry. The add/delete operations immediately save the affected store.

All certificates written by `addServerCertificate` and `addClientCertificate` use `KeyStore.setCertificateEntry`, which creates certificate-only entries. `JFTPKeyManager` initializes `KeyManagerFactory("SunX509")` from the client store and client-store password, then delegates all `X509KeyManager` callbacks. Since the UI imports certificates only, it provides no private-key identity import path; usable client-certificate authentication depends on an externally populated client store containing compatible key entries. Do not silently convert formats, change aliases/passwords, or imply that a certificate-only entry is a client identity. Decide any identity import/configuration work as separate scope.

The JKS type and `SunX509` algorithm names are provider assumptions rather than serialized-format documentation. A migration to PKCS#12, provider defaults, or new password handling must preserve or deliberately migrate existing files and settings, with backups and isolated compatibility fixtures.

## Application preferences and favorites persistence

`JFTP.DATA_HOME` is `${user.home}/.jftp/data`; `preferences.ser` and `favorites.ser` are stored there. These locations are source facts reported from `JFTP.java` and `FavoritesManager.java` by the application-workflow analysis; this subtask did not read those application classes in full.

`JFTPPreferences` is stored as a Java-serialized object in `preferences.ser`. Certificate-store path fields are ordinary strings; server/client JKS passwords and proxy password are `char[]` fields. The default store paths are the two files above, and both store password arrays default to the literal `changeit`. No password obfuscation is applied to these preference fields before Java serialization. Other serialized fields include UI and connection configuration; exact serialization compatibility is tied to the class definition/serial UID and Java object graph. `preferences.ser` should be treated as sensitive local state, not a safe interchange format.

Favorites are also Java serialized. `RemoteHost.password` is a `String` in the serialized host object. `FavoritesManager` wraps the favorites object in `SealedObject` using `Cipher.getInstance("AES")` and a fixed hard-coded 16-byte key, then writes `favorites.ser`. If cipher setup is unavailable, code falls back to serializing the plaintext list. Reading an older plaintext-list format immediately rewrites it through the current save path. The fixed-key reversible wrapper is obfuscation, not meaningful protection from someone who can read the application and file. Do not copy real `preferences.ser`, favorites, passwords, or live keystores into fixtures or logs.

## Failure, concurrency, and compatibility notes

Certificate/key store loading can fail during TLS setup before the FTP connection is attempted; the caller's connection flow must surface that exception. Missing bundle resources used by the dialogs invoke `ResourceLoader`'s `System.exit(1)` path during class initialization. TLS warning and certificate dialogs are Swing UI, while `checkServerTrusted` is invoked as part of the SSL handshake; invoking modal Swing code on a handshake thread can block that handshake until the user responds. The trust decision is stored in a field on the manager and is not persisted unless the user separately installs the chain.

The source uses deprecated `X509Certificate.getSubjectDN()` / `getIssuerDN()` accessors. The scoped source scan found no `sun.*` or `com.sun.*` imports. `SSL`, `SunX509`, JKS, and Java object serialization require explicit compatibility coverage when dependencies/JDK baselines change; this analysis did not run a compiler or resolve provider behavior on another JDK.

## Minimal-startup boundary and phase order

For the first modernization checkpoint, preserve the existing data directory, serialized preferences/favorites, raw configured JKS paths, certificate aliases, server-certificate trust UI, and FTPS session modes. Use a fresh temporary user home, not the developer's profile, and first characterize startup and ordinary FTP without exposing real credentials. Validate serialized preferences and favorites before touching TLS, then validate existing JKS load/save against copied synthetic stores, then run controlled local FTPS cases. Only after that baseline should implementation work change provider selection, trust validation, password protection, storage format, or client identity handling. Each of those changes has separate migration and user-visible behavior implications.

The repository-level modernization plan should keep storage migration, TLS policy, archive security, and Swing worker replacement in ordered, independently reviewable phases. Do not combine these changes under a general cleanup step.
